# AGENTS.md — правила работы с Quick-Install

Этот файл предназначен для любых coding-агентов и AI-ассистентов. Он действует на
весь репозиторий. Явная задача пользователя имеет приоритет; более близкий
`AGENTS.md` в подкаталоге может уточнять правила только для этого подкаталога.

## 1. Перед началом работы

1. Полностью прочитай `ARCHITECTURE.md` и файлы, относящиеся к задаче.
2. Уточни фактическую структуру и текущие имена функций поиском по репозиторию —
   документация может отставать от кода.
3. Проверь незавершённые локальные изменения и не перезаписывай чужую работу.
4. Не расширяй область задачи без необходимости. Диагностика не означает
   автоматическое исправление, если пользователь просил только аудит.
5. Если меняется внешний формат или API, сверяйся с актуальной официальной
   документацией проекта, а не с памятью или случайным примером.

## 2. Карта проекта и границы подсистем

- `setup.sh` — первичная установка QI и создание команды `qi`.
- `src/` — основной интерактивный Bash-инструмент.
- `ansible/` — декларативное развёртывание тех же серверных компонентов.
- `vpnguard/` — отдельное Go-приложение VPN Guard.
- `ARCHITECTURE.md` — источник правды о структуре, функциях и потоках данных.

VPN Guard не должен изменяться как побочный эффект работы над `setup.sh`, `src/`
или Ansible. Меняй `vpnguard/` и связанные с ним функции в `src/05_apps.sh` только
когда пользователь явно включил VPN Guard в задачу.

## 3. Обязательная синхронизация документации

Обновляй `ARCHITECTURE.md`, если выполнено хотя бы одно из условий:

- добавлен, удалён или переименован файл либо каталог;
- добавлена или удалена пользовательская функция, команда, роль или пункт меню;
- изменилась иерархия меню либо последовательность загрузки модулей;
- изменились глобальные переменные, серверные пути или формат конфигурации;
- изменился поток данных, внешний интерфейс или важное значение по умолчанию.

Документируй текущее поведение, а не план или желаемое будущее состояние.

## 4. Bash: архитектура и стиль

- `src/main.sh` загружает модули `00_globals.sh` … `06_diagnostics.sh` по порядку.
- Файлы-модули при `source` только объявляют переменные и функции: не запускай в
  них действия или меню на верхнем уровне.
- Пользовательские действия называй `do_*`, меню — `menu_*`. Общие небольшие
  операции размещай в `01_helpers.sh` с ясным глагольным именем.
- Локальные переменные объявляй через `local`, подстановки заключай в кавычки.
- Сохраняй реальный код возврата команды; ошибка не должна превращаться в
  успешное сообщение или продолжение опасной операции.
- Новая операция должна быть повторяемой либо явно предупреждать о последствиях.

### Единый интерфейс

- Используй `header`, `menu_section`, `menu_item`, `menu_back`, `read_choice`,
  `confirm_action`, `info`, `success`, `warn`, `error` и `press_enter`.
- Не создавай локальный визуальный стиль или собственный формат выбора, если
  общий helper уже решает задачу.
- Один пункт меню выполняет одно понятное действие. Подтверждение требуется перед
  удалением, перезаписью, сбросом, остановкой сервиса и изменением сетевого доступа.
- Заголовок, родительский раздел, нумерация, возврат и сообщения об ошибках должны
  вести себя одинаково во всех меню.

### Безопасность shell-операций

- Не исполняй сеть напрямую через `curl | bash`, `wget | sh`, process substitution
  или `eval`. Сначала скачай во временный файл, проверь результат и только затем
  запускай. Используй `download_atomic` и `run_remote_script`, где это подходит.
- Конфигурации меняй через временный файл или резервную копию; перед заменой
  проверяй непустой результат и синтаксис.
- Docker Compose вызывай через `ensure_docker`, `compose_run` и
  `compose_validate`, кроме автономных скриптов, развёрнутых на сервере.
- Для IP, портов, диапазонов и протоколов используй общие валидаторы.
- Никогда не применяй `chmod 777`. Секреты и Compose-файлы с токенами — `0600`;
  обычные исполняемые файлы — максимум необходимых прав.
- При включении UFW сначала разреши фактический SSH-порт текущего подключения.
  Не отключай обязательные ICMP-типы вместе с echo-request.
- Systemd-юниты и сетевые правила делай идемпотентными: повторный запуск не должен
  добавлять дубликаты.
- Не используй широкие `kill`, удаление по непроверенному glob и разрушительные
  Git-команды. Удаляемая или перезаписываемая цель должна быть точной и проверенной.

## 5. Ansible

Если изменение существует и в shell-сценарии, и в Ansible, сначала реализуй и
проверь shell-вариант, затем перенеси то же поведение в Ansible.

- Предпочитай специализированные модули и FQCN (`ansible.builtin.*`,
  `community.docker.*`, `community.general.*`) вместо `shell` и `command`.
- Задачи должны быть идемпотентными. Для неизбежных команд корректно указывай
  `changed_when`, `failed_when`, `creates` или условия запуска.
- Не зашивай токены, пароли и реальные IP в репозиторий. Используй host vars,
  Ansible Vault, `no_log: true` и права `0600`.
- Обязательные переменные проверяй ранним `assert` с понятным сообщением.
- Опциональные роли должны управляться флагами из `group_vars/all.yml`.
- Новую внешнюю collection добавляй в `ansible/collections/requirements.yml`.
- Для Remnawave Node используй контракт Compose, выданный панелью:
  `NODE_PORT`/`node_port` и `SECRET_KEY`/`node_secret_key`. Доступ к порту ноды
  ограничивай адресом `panel_ip`.
- Шаблон Compose с секретами не должен попадать в diff или иметь права чтения для
  всех пользователей.

## 6. VPN Guard — только при явной задаче

- Go-код форматируй `gofmt`; HTTP-клиенты строятся на стандартном `net/http`.
- Баллы скоринга имеют тип `float64`; логирование использует префикс `vpnguard:`.
- Долгий AI-анализ не должен блокировать обработку логов.
- При добавлении поля конфигурации синхронно обнови:
  1. `vpnguard/config/config.go` — структура, defaults и validation;
  2. `vpnguard/vpnguard.yaml.example`;
  3. генерацию и, если нужно, меню настроек в `src/05_apps.sh`.
- Не меняй порядок AI fallback или формат меток провайдера без явной причины и
  теста затронутого поведения.

## 7. Секреты и пользовательские данные

Нельзя добавлять в код, примеры, логи или коммиты:

- API keys, JWT, Telegram bot tokens, пароли и приватные ключи;
- реальные `.env`, рабочие `vpnguard.yaml` и Ansible Vault password files;
- приватные IP/домены пользователя, если они не были явно предназначены для
  публичного примера;
- содержимое `vpnguard/qwen/` или другие устаревшие эксперименты с токенами.

В примерах используй очевидные placeholder-значения и документационные сети
`192.0.2.0/24`, `198.51.100.0/24` или `203.0.113.0/24`.

## 8. Проверки перед завершением

Выполняй применимые проверки и сообщай, что именно не удалось запустить.

### Bash

```bash
bash -n setup.sh src/*.sh
shellcheck setup.sh src/*.sh
```

Дополнительно проверь изменённые валидаторы и генераторы небольшими smoke-тестами.
Для Compose-конфигураций используй `docker compose config`.

### Ansible

```bash
ansible-galaxy collection install -r ansible/collections/requirements.yml
cd ansible
ansible-playbook --syntax-check -i inventory.ini deploy.yml
```

`--check` запускай только на тестовом хосте и учитывай, что команды создания swap,
WARP и некоторые Docker-операции могут требовать отдельного сценария проверки.

### VPN Guard

```bash
cd vpnguard
go fmt ./...
go test ./...
```

Не запускай форматирование всего Go-модуля, если задача не относится к VPN Guard.

## 9. Критерии готовности

Работа завершена, когда изменение соответствует запросу, не затрагивает соседние
подсистемы без причины, ошибки обрабатываются явно, документация синхронизирована,
секреты не раскрыты, а применимые проверки прошли либо их отсутствие честно
зафиксировано в итоговом сообщении.
